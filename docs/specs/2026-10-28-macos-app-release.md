# Spec: release the macOS app

Date: 2026-10-28. Status: accepted as D50 (2026-10-29), which amends D35.

## Problem

The macOS app (D35) ships only as a local build: `macos/bundle.sh` makes an ad-hoc signed
`Skillcask.app` and a zip, and CI only tests it. Users get the CLI from Homebrew, npm, crates.io or
a release archive, but no app. A zip passed around today is blocked by Gatekeeper on any other Mac
(`spctl -a -vv`: `rejected`), and testers have to clear the quarantine flag by hand.

Goal: every tagged release also ships an app that macOS accepts like any other downloaded app, and
one Homebrew install gives both the `skillcask` command and the app.

## Constraints

- **Gatekeeper.** A downloaded app opens with one confirmation only when it is signed with a
  Developer ID and notarized. Apple silicon runs an ad-hoc signature, but Gatekeeper rejects it as
  soon as the file carries `com.apple.quarantine`; macOS 15+ then wants System Settings › Privacy &
  Security › Open Anyway, after every update.
- **Homebrew casks quarantine** what they install. `--no-quarantine` is gone (deprecated in
  Homebrew 5.0, removed in 6), and since 2026-09-01 `homebrew/cask` disables casks that fail
  Gatekeeper. Third-party taps (ours, `puniserv/homebrew-tap`) still load them, and some strip the
  quarantine in `postflight`; that bypasses Gatekeeper instead of passing it.
- **Homebrew formulae do not quarantine.** An app inside a formula opens even ad hoc, but it lives in
  the Cellar, not in `/Applications`: no Launchpad, and Spotlight finds it only by chance.
- **A tap cannot hold a formula and a cask under the same name** without `brew install skillcask`
  picking the formula and hinting at `--cask`.
- `release.yml` is generated by `dist` and hand-edited (AGENTS.md). Every extra hand edit must be
  re-applied after `dist generate`.
- The app is already built to notarize: hardened runtime, inside-out signing (helper, then app), no
  `--deep`, no App Sandbox, bundle id `io.github.puniserv.skillcask` (`macos/bundle.sh`).

## Proposal

### 1. Signed and notarized zip on every release

Job `publish-macos-app` in `release.yml`, after `host`, on `macos-26` with the same Xcode as CI's
`macos-app` job, in the `release` environment:

1. Downloads the two darwin CLI archives from the release, checks their `.sha256` and joins the
   binaries with `lipo`, so the app carries exactly the released CLI.
2. Imports the Developer ID certificate into a temporary keychain.
3. Runs `SKILLCASK_CLI=<universal cli> SIGN_IDENTITY="Developer ID Application: …" macos/bundle.sh`.
4. `xcrun notarytool submit <zip> --key … --key-id … --issuer … --wait --output-format json` and
   fails unless `status` is `Accepted`: `--wait` exits 0 on `Invalid` too. On failure it prints
   `notarytool log <id>`.
5. `xcrun stapler staple Skillcask.app`, then deletes the zip from `bundle.sh` (made before the
   staple, so it has no ticket) and zips again with `ditto -c -k --keepParent`.
6. Checks `spctl -a -vv` says `accepted` / `Notarized Developer ID`, then uploads
   `Skillcask-X.Y.Z-macos-universal.zip` and its `.sha256` to the GitHub Release, with
   `macos/install-app.sh` as `skillcask-app-installer.sh`, so
   `releases/latest/download/skillcask-app-installer.sh` installs the app without Homebrew.
7. Deletes the temporary keychain and the `.p8` file (`if: always()`).

The import uses `security import`, not OpenSSL: Keychain exports the `.p12` with RC2-40, which
OpenSSL 3+ reads only with `-legacy`. Verified by hand on 0.10.0 with the current `bundle.sh`
(no change needed): notarization `Accepted` with no issues, `stapler validate` ok, `spctl`
`accepted, source=Notarized Developer ID`.

It is a hand edit of `release.yml`, not a dist custom publish job (`publish-jobs = ["./…"]`): dist
skips custom publish jobs on pre-releases, and a pre-release tag is how the job gets tested without
publishing to Homebrew and npm. `announce` does not wait for it, so a failed notarization leaves the
CLI release intact; rerun the job, or the whole run, once fixed.

### 2. Homebrew: a cask next to the formula

- Formula `skillcask` (unchanged, from dist): the CLI on macOS and Linux.
- Cask `skillcask-app` in `puniserv/homebrew-tap`: installs `Skillcask.app` into `/Applications`,
  `depends_on formula: "puniserv/tap/skillcask"`, `depends_on macos: :sonoma`, `zap` for the app's
  preferences. Job `publish-homebrew-cask` (after `publish-homebrew-formula`, which pushes to the
  same tap, and `publish-macos-app`; skipped on pre-releases like the formula) reads the zip's
  `.sha256` from the release, writes the whole cask and pushes it with the existing
  `HOMEBREW_TAP_TOKEN`. It gets no signing secrets.

`brew install puniserv/tap/skillcask puniserv/tap/skillcask-app` then gives both. Both names, because
Homebrew refuses to load anything from a third-party tap that is not named on the command line or
listed by `brew trust`, and a dependency is neither. Users who install only the formula get no app.

### 3. `skillcask app`

A macOS-only command that opens the app via LaunchServices (`open -b io.github.puniserv.skillcask`),
so it works wherever the app is installed. When none is found, it names the cask and the release zip.
Elsewhere it fails with `MANIFEST` and a short message. No other behaviour: it passes no arguments
and starts no process besides `open`.

### Rejected

- **App inside the formula.** It works without an Apple account, but the app stays in the Cellar and
  `dist` regenerates the formula every release, so it needs a patch step in the publish job. Fallback
  only, if notarization is not possible.
- **Cask that strips the quarantine.** It turns off the check that protects users from a tampered
  download.
- **One cask `skillcask` with `app` and `binary` stanzas** replacing the formula on macOS: it splits
  macOS and Linux installs and clashes with the formula name.
- **Sparkle or another in-app updater**: Homebrew and the release zip cover updates; an updater adds
  network code to an app that has none (D35). A notice that a release exists is not an updater:
  D51 asks through the CLI and leaves the update to Homebrew or the zip.

## Secrets

Environment secrets of the GitHub environment `release`, not repository secrets, so only the
signing job (`environment: release`) gets them:

| Secret | What |
|---|---|
| `MACOS_CERTIFICATE_P12` | Developer ID Application certificate with its private key, base64 |
| `MACOS_CERTIFICATE_PASSWORD` | password of the `.p12` |
| `MACOS_SIGN_IDENTITY` | `Developer ID Application: <name> (<team id>)` |
| `APPLE_TEAM_ID` | the team id |
| `APP_STORE_CONNECT_API_KEY_P8` | App Store Connect team key for `notarytool` (role Developer), base64 |
| `APP_STORE_CONNECT_KEY_ID`, `APP_STORE_CONNECT_ISSUER_ID` | its key id and issuer id |

Set the file secrets with `base64 -i <file> | gh secret set <NAME> --env release`, so they never
pass through the clipboard or shell history, and delete the local copies afterwards.

Repository settings that keep a signed build behind a review:

- Environment `release`: required reviewers (the certificate owner and the maintainer), "Allow
  administrators to bypass" off, deployments only from tags matching `v*`.
- Tag ruleset on `v*`: restrict creations, updates and deletions, bypass only for the maintainer.
  Without it, anyone with push access could tag a commit with a changed `release.yml` and get a
  signed build.

The certificate owner owns all seven secrets and rotates them yearly: a new App Store Connect key
and a `.p12` exported with a new password, next by 2027-10-29. That also comes before the
certificate expires on 2027-11-27. Builds already notarized keep working. On a leak, the owner revokes the
API key in App Store Connect and, if needed, the certificate. Actions stay pinned to a commit sha;
signing and notarizing use `security` and `xcrun` directly, with no third-party signing action.

## Testing

- `spctl -a -vv` and `xcrun stapler validate` on the uploaded zip, in the job.
- Manual, once per change to the job: download the zip in a browser on a Mac that never built
  skillcask, open it, expect the single "downloaded from the internet" prompt;
  `brew install puniserv/tap/skillcask puniserv/tap/skillcask-app`, then `skillcask app`.
- `macos/Scripts/smoke-app.sh` against the notarized bundle.

## Resolved questions

- Cask name: `skillcask-app`, next to the formula `skillcask`.
- The app keeps preferring its bundled CLI: it stays at the version it was built and tested with.
- Notarization time: `notarytool --wait --timeout 30m`. A late or rejected notarization fails only
  `publish-macos-app`; the CLI release is already out, and a rerun of the failed jobs attaches the
  app later.
